# Harvest report page: prototype write-up

**Status: throwaway prototype, built to answer a design question. Not integrated into `skills/harvest/`.**
Branch: `prototype/harvest-report`. Everything lives in `prototypes/harvest-report/`.

Written for the person reviewing and iterating on the UI/UX. Section 7 is the list of things I
already know are rough, so you don't have to rediscover them.

## 1. The question

Step 3 of `harvest` is a code review: the human reads a dozen or more features, marks several, and
has questions about a few. Doing that one chat message at a time is slow. The idea (from the user):
generate an optional, local HTML page from the ledger where the human can mark entries, type
questions and notes, and save the state to a file the agent reads back, like GitHub's batched review
(draft comments across the whole thing, submit once).

Two rules keep it from becoming an anti-pattern:

1. **The ledger stays the single source of truth.** The page is generated from the ledger and
   produces a separate *responses* file. The agent ingests that into the ledger. The page never
   becomes a second ledger.
2. **A fixed template, not bespoke HTML.** One template ships with the skill; a small script injects
   the data. The agent never hand-writes the page.

The loop: `/harvest` → "generate report" → human marks up the page and exports responses → agent
ingests, answers every question in one pass, applies the picks, regenerates the page with answers
inline → next round. Chat handles depth; the page handles the broad first pass.

Questions this prototype tries to answer: Is the page better than chat for the broad pass? Which save
path works? Does the ledger format parse reliably? Is it worth shipping?

## 2. What is here

| Path | What |
|---|---|
| `report-template.html` | The page. One file, inline CSS and JS, no CDN, no framework. Data is injected at `__HARVEST_DATA__`. |
| `render_report.py` | Python stdlib only. `render` parses a ledger and writes `report.html`; `check` validates a responses file and compares it with the current ledger. |
| `responses.schema.md` | The responses JSON shape (`harvest-responses/1`). |
| `ingest.md` | Draft agent-facing instructions for reading a responses file back into the ledger. |
| `fixture/origin-main.md` | **Synthetic** round-0 ledger: 17 features, `Plumbing`, `Head-only`, 2 set-aside items. |
| `fixture/origin-main.after-round1.md` | The same ledger after I applied `ingest.md` to the round-1 responses by hand. |
| `test_round1.py`, `test_round2.py` | Playwright drivers for the full loop (section 4). |
| `shots/` | Screenshots from the test runs. |
| `out/` | Output of the last test run (rendered pages, exported responses). Regenerated by the tests; `out/profile/` is git-ignored. |

### Run it

```bash
cd prototypes/harvest-report
python3 render_report.py render fixture/origin-main.md -o /tmp/report.html   # then open /tmp/report.html in Chromium
python3 test_round1.py     # needs python3 playwright + Chromium
python3 test_round2.py     # run after test_round1
python3 render_report.py check out/responses.json fixture/origin-main.md
```

### About the fixture

The user's real ledger (`~/code/curry/matt-daemon/.git/harvest/curry.md`) was **not reachable** from
the cloud container I built this in, so I never read it. The fixture is invented (a fictional job-queue
daemon fork) but follows the entry template in `skills/harvest/SKILL.md`: title, description, `Why:`,
the six bullets, optional `Notes:`. It has real dependencies between entries (F4 → F3 → F2, F12 → F11,
F10 → F9 → F1 and so on), one `landed: <branch>` entry (F1), one entry already picked (F8) and one
already left (F14), entries with `Notes:` (F4, F16, S1, S2), and set-aside items with evidence notes.
**The parsing findings below therefore come from the spec, not from an old-format ledger.** Running
`render_report.py render <real ledger> -o x.html` on a real one prints every parse warning.

## 3. What the page does

- **Table**, in dependency order (Kahn sort, ties by id), with `Plumbing`, `Head-only` and set-aside
  items in their own groups at the end. Columns: id, title + description, fit, depends on (chips
  coloured by the dependency's current state, plus a "needed by" line), status, mark.
- **Expand a row** for the full entry (all fields, "needed by" chips, the verbatim ledger text, earlier
  notes and answers) and, beside it, this round's response: warnings, comments, composer.
- **Mark** each entry `cherry-pick`, `rework`, `rebuild` or `left`. Clicking the active button
  un-marks it. `↺` returns to the ledger's status. A batch field appears when an entry is picked; the
  placeholder shows the default batch name (first four words of the title, as `SKILL.md` specifies).
- **Comments:** any number of questions or notes per entry (question/note toggle, Ctrl+Enter adds), plus
  a general-notes box at the bottom.
- **Dependency warnings:** a picked entry whose dependency is neither picked nor landed gets an amber
  "needs F4 (left)" tag, and the dependency gets "needed by picked F5". The entry's panel offers a
  "say how to cut it" field; filling it clears the warning and is exported as a `cut`.
- **Landed / set aside** rows are visibly different: green left border, hatched background, muted
  title, no mark controls.
- **Earlier rounds:** answers from the ledger's `Notes:` show inline under their questions. Questions
  from a previous responses file that the ledger has no answer for show as "awaiting answer".
- **Batches panel** groups the picks by batch name and notes when a batch builds on one in another
  batch.
- **Counts and filters** in a sticky header: open / picked / left / landed / set aside / questions /
  dependency warnings; filters for open, picked, left, with comments, warnings.
- **Parse warnings** from the renderer are shown in a banner on the page.
- **Persistence and saving:** see section 5.

## 4. Testing and results

Drivers: Playwright (Python) with the pre-installed Chromium, headless, 1320×900. Both scripts pass.

### Round 1 (`test_round1.py`)

| Step | Result |
|---|---|
| Render fixture | 21 entries, round 1, 0 parse warnings |
| Order | Every dependency appears before its dependents; `Plumbing`, `Head-only`, `S1`, `S2` are last |
| Mark F2, F3, F6, F9, F10, F4 (left), F12 (left), F5; F8 and F14 left as the ledger had them | Counts match |
| F5 picked while F4 is left | F5 shows "needs F4 (left)", F4 shows "needed by picked F5", header shows "1 dependency warning" |
| F9 picked, depends on F1 (landed) | No warning |
| 3 questions, 1 note, 1 general note | Present in export |
| Reload | State identical |
| Close the browser, reopen the same profile | State identical (so `localStorage` on `file://` survives restarts in Chromium) |
| Export | Downloads `responses.json` |
| Copy responses | Clipboard text is `Harvest responses, round 1 …` plus a fenced JSON block |
| File System Access | See the caveat below. The write, and the rewrite on a later change, work |
| Export vs copy vs file contents | Identical, ignoring `created` |
| `render_report.py check` | Exit 0 against the fixture ledger |
| Page errors | None |

**What the File System Access test does and does not show.** Headless Chromium cannot drive a native
save dialog, and OPFS is blocked on `file://` (`SecurityError`), so I could not use a real handle. The
test swaps in a **fake handle** (`createWritable`/`write`/`close`, permission always granted) for
`showSaveFilePicker`. That tests my write/rewrite logic only. **Untested:** the real picker UI, the
permission prompt, whether a real handle survives a reload through IndexedDB, and what happens when
permission lapses. The page does confirm that `showSaveFilePicker` exists and `isSecureContext` is true
on a `file://` page in this Chromium; the test prints both.

### Ingest by hand

I applied `ingest.md` to a copy of the ledger, following it literally
(`fixture/origin-main.after-round1.md`; `diff` it against `fixture/origin-main.md`):

- `Status:` lines became `picked: <mode>, batch: <name>` or `left`.
- Each question became a dated `Notes:` sub-bullet with an id and an answer; the note became a `Note`
  line; the general note and `Report: round 1 ingested …` went in the header.
- The answers are invented (the fixture has no code behind it).

Things I noticed doing it:
- The `check` step was useful: after ingest, re-running it on the same responses file reports
  `STALE: responses round 1 but the ledger already records round 1 ingested`, so an already-spent file
  can't be applied twice.
- `check` reported the F5/F4 dependency as advisory only (exit 0). I added that after the first run
  showed `check` calling a response with an unresolved dependency "OK".
- Nothing in `ingest.md` was ambiguous enough to stop me, but it is untested by anyone but its author.

## 5. Save paths compared

| | Browser storage + Export | Copy responses | File System Access |
|---|---|---|---|
| Works in | Everywhere | Everywhere | Chromium only |
| Agent gets the file by | Human saying where it landed | Human pasting into chat | Reading the chosen path directly |
| Works when the agent can't see the human's disk (cloud session) | No | **Yes** | No |
| Silent after setup | No (click each time) | No | Yes (rewrites on every change) |
| Setup / failure modes | Filename collisions in Downloads | Clipboard permission (modal fallback exists) | Picker, then a permission re-grant after each reload; real behaviour untested |

`localStorage` is the working draft in all three. Caveats: in Chromium all `file://` pages share one
storage origin (the key therefore includes head SHA and round), and clearing site data loses the draft.

**Recommendation:** localStorage draft + **Copy responses** as the primary hand-back (it is the only
path that works when the agent runs remotely, as this session does), Export as the fallback, and File
System Access only as an optional extra. If it ships, name the download `responses-r<round>.json`; I
kept `responses.json` because the brief said so.

## 6. Observations

### Page versus chat

Better on the page: seeing all features at once; marking several and queueing questions without
waiting for answers; dependency warnings updating live; seeing the batches take shape; the agent
answering everything in one pass.

Still better in chat: follow-ups on an answer; questions whose answer reshapes the ledger (a split, a
new dependency); deciding how to cut a dependency (the page only takes a one-line note).

### Ledger format: fragile points, and proposed `SKILL.md` changes

1. **Header fields are unspecified.** I guessed `Base: upstream/main @ 4be19e2`. Propose one
   `Key: value` per line with the exact keys.
2. **`Plumbing` and `Head-only` have no id.** I used `### Plumbing. title`. Propose that form.
3. **Set-aside items have no template.** I used `S<n>` ids, the normal entry fields, and
   `Status: landed: already on base`; the renderer treats that status as "set aside". Propose it.
4. **`Notes:` has no format.** Propose dated sub-bullets: `- 2026-10-09 Q (r1.q2): <question> A: <answer>`
   and `Note (r1.q3): …`. The id is what lets the page match answers to questions across rounds.
5. **`Depends on:` is free text.** The parser takes every `F<n>` it finds, so "F2 (not F5)" would add
   F5. Propose ids first, then prose after a `;`, and a `cut:` convention.
6. **Ids are not stable across splits or resumes.** Propose: never reuse or renumber; a split keeps the
   id on the larger half.
7. **Add a header line `Report: round N ingested <date>`.** The renderer and `check` use it to tell a
   spent response file from a current one.
8. **`Fit:` must start with `aligned`, `tension` or `conflict`.** The parser relies on it; state it.

### How it would ship (Agent Skills layout)

```
skills/harvest/
  assets/report-template.html
  scripts/render_report.py
  references/REPORT.md        # schema + ingest steps, merged; loaded only when the human asks for a report
```

The one-line pointer for `SKILL.md`, at the end of step 2 and again in step 3:

> To review features in one batched pass instead of in chat, if the human asks, read [references/REPORT.md](references/REPORT.md).

### Worth integrating?

Yes, as an optional extra: about 400 lines of Python and a 36 KB page, no dependencies, and no change
to the ledger beyond the clarifications above. Costs: `render_report.py` must be kept in step with
`SKILL.md`'s ledger format, and a response-file protocol is one more thing for the agent to get right.
Most of the value comes from tightening the ledger format, which helps with or without the page. Not
yet tried: a real ledger, 30+ entries, or a human other than the author.

## 7. Known rough edges (please look at these first)

These are things I saw or suspect. None was reported to me by a user.

**Layout and density**
- The sticky header takes about 130 px of a 900 px viewport (title, five buttons, counts, filters).
  On a laptop that is a lot.
- The Status column mixes four things: a state chip, a "changed" tag, a batch input, and (when long) a
  wrapped branch name. The "changed" tag appears on every row the human has touched, so in a busy round
  it is noise.
- The Mark column has four buttons plus `↺`, and wraps to two lines at the 236 px column width.
- Row heights vary with comment tags and batch inputs, so the table jumps when you mark.
- I fixed one overflow while writing this up: a long `landed · harvest/…` branch name ran past its
  column. The screenshots in `shots/` were regenerated after that fix; the four sent earlier in chat
  were not.
- The default-batch placeholder is truncated in the input (`dead-letter-que`).
- The table has no responsive layout below about 980 px.

**Interaction**
- Clicking anywhere on a row toggles it, while the mark buttons, batch input and dependency chips inside
  it have their own handlers. Misclicks are likely.
- Every keystroke in a batch or cut field re-renders the whole table (focus is restored by a
  `data-k` hack). It is fast at 21 rows; not checked at 30+.
- Expanded rows are forgotten on reload; the question/note toggle is remembered between entries
  (deliberate, possibly wrong).
- Comments cannot be edited, only deleted and re-added.
- No keyboard shortcuts (j/k to move, 1/2/3/0 to mark would suit a 20-row pass).
- No undo.
- The "say how to cut it" field is a single line, and the "Warnings" filter shows entries on both sides
  of a dependency.
- "Reset draft" uses `confirm()`.

**Information design**
- Dependency order is correct but not visible as a structure (no grouping or indentation); chips are the
  only cue.
- Fit is a coloured word. The reason (the yardstick line it cites) is in a tooltip and the expanded
  panel only.
- The Batches panel is at the bottom; marking a batch name at the top and seeing it there needs a
  scroll.
- "Changed", "answered", "awaiting answer" and "needed by picked …" are all small tags with similar
  weight.
- Dark mode and colour contrast were not checked (the amber on cream for warnings is the likely
  problem).

**Accessibility**
- Mark buttons use `aria-pressed`; nothing else was considered (landmarks, focus order in the expanded
  row, announcement of warnings, contrast).

## 8. Questions I'd like a UI/UX reviewer to answer

1. Is a table the right primary view for 15–30 features, or would a list/board grouped by dependency,
   or by state, read better?
2. Should marking happen inline in the row, or in the expanded panel only, with the row showing results?
3. How should dependency problems be shown: tags on the row (current), a separate "problems" list, or
   inline in a dependency graph?
4. What belongs in the sticky header, and what could move out?
5. Is the question/note composer in the right place (the expanded panel), or should questions be
   capturable without expanding?
6. Does the round-2 view make it clear what is new (answers) versus what is carried over (marks that now
   live in the ledger)?
7. What is the best way to present the three save paths without making the human choose?
